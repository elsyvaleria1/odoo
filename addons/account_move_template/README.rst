Templates for the documents AgroMarin issues over and over: journal entries,
vendor bills, customer invoices, credit notes and outbound payments. A template
holds the journal, the partner, the accounts and the products; running it opens
a wizard that asks for the few things that change -- a date, an amount, a
partner -- and creates the document.

This module began as ``account_move_template`` from
`OCA/account-financial-tools <https://github.com/OCA/account-financial-tools>`_
and has since diverged: the upstream features built on ``opt_account_id``, an
overwrite dictionary and Python-computed amounts are **not** present here, and
everything below was added for this fork. It is no longer generated by
``oca-gen-addon-readme``; edit this file directly.

Configuration
=============

**Journal and account codes.** A template names its journal by *code*, not by
id, and each line names its account by *code prefix*. Both resolve at run time,
in the company the run belongs to, so one template serves every company that
uses the same chart of accounts and the same journal codes. The ``Journal`` and
``Account`` pickers next to them show what the stored code currently resolves
to; picking one fills the code. The journal must suit the document: a sale
journal for customer invoices and credit notes, a purchase journal for vendor
bills and refunds, a bank, cash or credit card journal for payments; a journal
entry may use any. A template is checked when it is saved, and a run looks only
at journals of the right kind.

Usage
=====

Journal entry templates
-----------------------

Give the template a journal code, ``Journal Entry`` as the move type, and one
line per journal item with an account prefix and a balance. Balances must sum
to zero, as on any entry. Run it from the ``Use Template`` button on the
template, or from ``Accounting > Create Entry from Template``.

Invoice and bill templates
--------------------------

Pick ``Vendor Bill``, ``Customer Invoice`` or either credit note. Lines carry a
product, a quantity, a unit price, taxes and an optional discount.

The wizard's ``Amount`` is the **untaxed total of the document** and is never
negative. It is distributed across the product lines, with the rounding residue
on the last one, so ``amount_untaxed`` equals what was typed -- unless a line
carries a discount, which still applies to its share. Each line decides how it
spends its share through ``Distribution method``:

``Collapse (one line, full amount)``
   One line, quantity 1, priced at the share. Use it for discounts, fees and
   single-item credit notes, where the template's own unit price is only a
   placeholder.

``Split (decompose into units of price_unit)``
   As many whole units at the template's unit price as the share pays for, plus
   one adjustment line for the remainder. The adjustment carries the same label
   and taxes as the units it completes. Use it for bills expressed as "N units
   at X". A line with no positive unit price -- its own or its product's --
   collapses instead.

Customising the lines
---------------------

The wizard holds no lines until ``Customize lines`` is ticked: a run derives
them from its header (template, amount, partner, company) when
it creates the document, so a header changed in the dialog always reaches every
line. Ticking ``Customize lines`` loads them for editing; from then on the run
creates exactly the lines shown, and changing the amount no longer reloads
them (changing the template or the company does).
A line takes the partner its template line names, else the document's.

Sections and notes
------------------

A line can be a ``Section`` or a ``Note`` instead of a product. They carry no
accounting value, take no share of the amount, and are written to the generated
document as display lines in sequence with the product lines around them.

Payment templates
-----------------

Tick ``Is payment``, choose the payment type and partner type, and give the
template a bank journal code. Template lines are not used. The wizard's
``Payment Amount`` is required, and the payment is returned **in draft** --
posting is left to whoever asked for it.

Third party
-----------

A run can carry a ``third_party_id``: the party a document is made out to in
place of the partner, such as the generic public for a customer who takes no
fiscal invoice. It is informational by default, so the partner stays on the
document. Tick ``Issue to the Third Party`` on a template to have that
template's documents issued to it instead -- the fiscal invoice of a discount
run is one of those. Leave it off wherever the partner himself has to be on the
document, as on the credit note that reduces his debt.

Multi-company
=============

A template may carry a company or leave it empty. An empty company means the
template is shared, and its journal code is validated against the companies the
user can act for. The run itself always resolves one company -- the wizard's
``multicompany_id`` if given, else the template's, else the active one -- and
resolves the journal and the accounts inside it. ``automation_account`` passes
the run's transaction company as ``multicompany_id`` when the run spans two
companies or the template has none.

Known issues
============

* The name of an archived template stays reserved: a new template cannot reuse
  it until the archived row is deleted. This follows the framework default for
  catalog-style name indexes.

Integrations
============

``automation_account``
   Calls the wizard from a server action, passing the runtime's partner, date,
   amount, third party and target company (the run's transaction company, for
   an intercompany run or a template without a company). It takes an
   ``auto_post`` flag and posts the result itself.

``marin``
   Draws a line's product at run time: from the payment product family the run
   names, or from a product category on the template line.

``l10n_mx_edi_account_move_template``
   Adds the CFDI usage code and payment method to the wizard and forwards them
   to the generated move.

``account_move_template_purchase``
   Grants buyers access to readable template sources in purchase autocomplete.

``account_move_template_sale``
   Grants salespeople access to readable template sources in sales autocomplete.

Autocomplete architecture
=========================

Accounting owns ``mixin.account.document.match``, the shared source schema,
query assembly and existing-move source. ``account.move.match`` exposes these
sources through ``account.move.invoice_source_id`` for both customer and vendor
documents. The legacy ``invoice_vendor_bill_id`` remains an API adapter and a
hidden view inheritance anchor.

``trade_account`` extends the source mixin with order columns and queries.
Purchase and Sales keep their concrete matching models and permission policies;
both use the same source dispatch and order-loading implementation. Their
selectors replace the Accounting selector only for the corresponding trade
role and document direction. Accounting chooses the selector through the shared
``_get_invoice_autocomplete_fields`` registration hook. Source onchanges use the
invoice pane as their authority, preventing the invoice and journal-item panes
from submitting duplicate CREATE commands for the same new line.

Accounting Document Templates extends the Accounting source mixin directly.
Templates therefore appear in Accounting without Trade installed and in both
trade selectors when their permission bridges are installed. No template query
or template-loading logic belongs to either bridge. Both bridges automatically
install with their respective applications and Accounting Document Templates.

Source providers declare their values through ``_select_document_columns``.
Extensions add typed defaults through ``_get_document_columns``, keeping every
UNION branch aligned without copying SELECT lists. Move ids retain their real
positive ids, order ids retain their negative ids, and templates use
``2**31 + template.id``. These virtual bigint ids are stable, disjoint from
int4 document ids, and exactly representable by the browser. Selection fields
are transient; the old template id calculation has no stored data to migrate.

Projection queries include each source model's ORM read policies. Loading a
source checks its read access again. Templates must be active, non-payment,
match the destination document type exactly, and belong to its company or all
companies. A company-less template resolves accounts in the destination company.

Existing documents and orders append lines; templates replace lines. Template
autocomplete shares account validation and move-line serialization with the
generation wizard, while preserving literal template prices, taxes and labels,
including zero prices and empty tax sets. It includes explicit units, discounts,
analytics, sections and notes. It preserves an existing
partner and reference, applies template payment terms, and leaves the destination
journal and currency in place. Account resolution completes before replacement;
an invalid source cannot clear existing lines.

Order loading compares linked lines' persisted origins, so selecting the same
order again also works on an unsaved document without duplicating its lines.
